# OwnDsh 产品官网 —— 规划设计

> 目标：为本项目（OwnDsh：DeepSeek Harness 的自托管团队控制面）规划一套**多页产品官网**。
> 参考：`deepseek.com/harness/`（开源产品页）、`dshdesktop.com/zh/`（客户端下载页）、`dshdesktop.com/zh/enterprise/`（企业版落地页）。
> 本文档是**规划与设计**；参考站结构来自实际抓取，本项目事实来自本机部署与仓库，均标注来源。

---

## 0. 结论（TL;DR）

| 项 | 结论 |
|---|---|
| 起点 | **改造上游已有的单页官网**（`src/website/`，1.1 MB，含真实截图与自托管字体），不是从零新建 |
| 现状差距（实测） | 线上 `owndsh.1024300.xyz`：`/` 200（29 KB）✅，但 **`/sitemap.xml` 404**、**`/enterprise/` 404** —— 正好是参考站的强项 |
| 站点形态 | **6 页多页站**：首页 / 企业版 / 部署与自托管 / 客户端下载 / 安全与合规 / 关于；加 404 与 sitemap |
| 与参考站的关系 | 首页学 `deepseek/harness`（一句话主张 + 可复制命令 + 真实截图叙事）；企业版学 `dshdesktop/enterprise`（编号价值点 + **痛点对照表** + 场景分区 + 留资）；下载区块学 `dshdesktop`（平台卡 + 当前设备识别 + 社会证明） |
| 关键立场反转 | 官网**公开可索引**（`index,follow` + sitemap + JSON-LD + OG），与 `/help/`、`/api-docs/` 的 `noindex` + 登录门禁**完全相反** |
| 技术选型 | 沿用上游 `website/` 的**零依赖静态站**范式（纯 HTML/CSS/JS + Node 白名单构建），样式令牌与字体复用 `/opt/owndsh/docs-assets`（与两个文档站同源） |
| 部署 | 三选一（Cloudflare Pages 现有域名 / 自有域名 + 本机 nginx `server_name` / 本机路径），产物完全相同，迁移成本≈改一处 base URL |
| 合规 | 必须写明**与 DeepSeek 官方无隶属关系**（README 已有此表述、参考站也都写明），并提供安全/数据处理说明与隐私口径 |
| 工期 | P1 首页改造 + 企业版 + 部署页 + SEO 基建 ≈ 3–4 人日；P2 域名/HTTPS/下载页 ≈ 1–2 人日；P3 多语言 + 案例/博客 ≈ 2–3 人日 |

## 1. 三个参考站的拆解（实测结构）

### 1.1 `deepseek.com/harness/` —— 开源产品页：**首屏即能动手**

| 区块 | 做法 | 我们该借鉴什么 |
|---|---|---|
| 顶栏 | logo + 语言切换 + GitHub / 开发者文档 / 社区插件 / 技术论文 | 顶栏只放"能立刻验证产品"的链接，不放营销入口 |
| Hero | 一句主张（**"一切皆插件"**）+ 三个 CTA + **可复制安装命令** + "快速体验 / 源码安装"两个 tab | 首屏必须给出**可复制命令**（我们的对应物是 `docker compose up -d --wait`），并区分"快速体验 / 源码部署" |
| 概念锚点 | "Agent = Model + Harness" | 我们也需要一个可复述的锚句：**"Agent 的自由留给员工，边界交给平台"** 或 **"Harness 给能力，OwnDsh 给秩序"** |
| 能力三卡 | Cordis 内核 / 插件提供能力 / 配置层自由组合（均带英文小标） | 三卡式讲清架构，英文小标提升专业感 |
| 叙事块 | 带**真实截图**的功能说明（设置页插件、Trajectory 视图） | 截图必须是真实界面，不用插画凑数 |
| 模式对比 | 四个运行模式卡片（标准/PTC/极简/创造） | 我们的对应物是**四个角色**（平台/模型/插件/审计管理员）或**四个治理面** |
| 开始使用 | 两条命令（npx / git clone） | 命令 + 复制按钮是转化主力 |
| 页脚 | 二维码、MIT、版权、**安全使用政策 / 数据处理说明** | 合规链接不是可选项 |

### 1.2 `dshdesktop.com/zh/` —— 客户端下载页：**把下载做成无摩擦**

| 区块 | 做法 | 我们该借鉴什么 |
|---|---|---|
| 顶栏 | 品牌 + 工作配方(Preset) / GitHub / **企业版** / 6 种语言 | 顶栏放"企业版"入口，是多页站的关键分流 |
| Hero | **中英并排双语标题** + 主下载 CTA + **三平台卡片（含"当前设备"识别与推荐）** | 客户端下载页照抄这个模式（macOS ARM/Intel、Windows） |
| 社会证明 | 累计下载计数 | 我们没有下载量时可换成"已部署实例/插件版本"等真实数字，**没有就不编** |
| 截图 | 真实工作界面 | 同上 |
| 社区 | 微信群二维码 + Discord | 我们至少要有 Issue/讨论区入口 |
| 页脚 | 版权 + **明确免责声明**（与 DeepSeek 无隶属关系）+ 团队背书 | 直接采用同样的免责口径 |
| 彩蛋 | Star 引导弹窗 | 可选，低成本高转化 |

### 1.3 `dshdesktop.com/zh/enterprise/` —— 企业版：**给决策者的说服路径**

| 区块 | 做法 | 我们该借鉴什么 |
|---|---|---|
| Hero | 主张式标题（"让每位员工用好 Agent，让企业始终掌握边界"）+ **双 CTA（咨询 / 看开源版）** | 企业页必须给"先看开源版"的退路，避免把技术决策者挡在门外 |
| 价值点 | 4 个**编号**卡片（统一身份 / 模型供给 / 成本额度 / 可追溯） | 我们正好有对应的 4 件事实：LOCAL/LDAP/OIDC、集中托管模型与凭据、Token/RPM/并发配额、审计与用量 |
| 核心说服 | **"分散使用时 vs 接入后"对照表**（4 行痛点 → 4 行解法） | **这是全站最有说服力的一块**，必须做，且每行都要有技术事实支撑 |
| 适用场景 | 3 个场景，带英文标签（SCALE / GOVERN / OPERATE） | 我们：**规模化推广 / 合规与数据边界 / 多部门多模型运营** |
| 交付方式 | 定制客户端、对接既有身份与模型平台、部署分发与支持 | 我们：私有化部署、身份源对接、模型网关接入、升级与备份支持 |
| 背书 | 母公司能力 + **两排客户 logo 墙** | ⚠️ 我们没有客户 logo，**不要伪造**；可换成"可验证的技术事实"（如实测资源占用、API 数量、错误码稳定性） |
| 留资 | 底部表单（称呼/手机号/公司/需求）+ 隐私说明 | 见 §9 的取舍：**不自建后端** |

## 2. 本项目现状与差距（已核实）

| 项 | 事实 | 来源 |
|---|---|---|
| 上游官网 | 单页站，1.1 MB，纯 HTML/CSS/JS，零第三方依赖；Node 标准库白名单构建（`build.mjs` 只发布 `index.html/404.html/styles.css/script.js/_headers/assets`） | `/opt/owndsh/src/website/` |
| 已有素材 | `console.jpg`、`desktop.jpg`（真实截图）、whale 品牌图（静态+动态）、**自托管 Inter 字体** + 字体与 Lucide 许可证 | 同上 `assets/` |
| 已有文案骨架 | h1/h2 逐条："团队有章可循。把管理交给平台。"/"集中的是管理。"/"从一条命令，"/"开始之前。"/"属于你的 Harness。" | `website/index.html` |
| 已有转化 | `docker compose up -d --wait`、`git clone https://github.com/boe1900/owndsh.git` | 同上 |
| 已有 SEO | `<title>` + `og:type/locale/title/description`（zh_CN） | 同上 |
| 线上状态 | `https://owndsh.1024300.xyz/` → **200（29 KB）**；`/robots.txt` → 200（1.8 KB，平台托管）；**`/sitemap.xml` → 404**；**`/enterprise/` → 404** | 本机实测 |
| 本站已有资产 | 控制台（`/`）、帮助中心（`/help/`，登录门禁）、API 参考（`/api-docs/`，登录门禁）、共享主题与字体（`/opt/owndsh/docs-assets`） | 本次会话已建成 |
| 仓库里的产品事实 | 4 类管理员能力矩阵、LOCAL/LDAP/OIDC、97 个 API / 42 个稳定错误码、插件分发与签名开关、会话治理与审计、Docker Compose 自托管（2C/3.6G 实测可跑） | `README.md`、`docs/v1-product-feature-catalog.md`、`DEPLOYMENT.md`、契约 |

**差距清单（按价值排序）**
1. 缺**企业版落地页** → 决策者没有落点（参考站有，且是其主要转化路径之一）
2. 缺 **sitemap.xml** 与结构化数据 → 搜索引擎收录质量差
3. 单页承载不了"部署/下载/安全/关于"这些**独立搜索意图**（例如有人只搜"LDAP 单点登录""离线部署"）
4. 缺**多语言**（参考站 2–6 种；我们至少中文 + 英文）
5. 缺与**本站文档体系**（帮助中心 / API 参考）的互链，文档资产没有被官网利用
6. 缺**免责声明与合规页**（参考站都写在页脚显眼处）

## 3. 目标与非目标

### 目标
1. **三类受众各有落点**：开发者/运维（→ 部署命令、GitHub）、企业与 IT 决策者（→ 企业版、治理价值、留资）、员工（→ 客户端下载、接入方式）。
2. **首屏即可动手**：一句话主张 + 一条可复制命令 + 真实截图。
3. **可被搜索到**：`index,follow` + sitemap + JSON-LD + 每页独立 title/description + OG 卡片 + canonical + hreflang。
4. **与文档体系互链**：官网 → 帮助中心 / API 参考 / 控制台；文档站 → 官网。
5. **合规且不夸大**：每条对外表述都能对应仓库事实或实测数据；明确与 DeepSeek 官方无隶属关系。
6. **零依赖、可离线**：无第三方 CDN/字体/分析脚本；构建在容器内完成（宿主无 node）。

### 非目标
- ❌ 不做账号体系、在线试用环境、付费/结算（本部署不提供多租户注册）。
- ❌ 不做内容营销站（博客/案例库）——留到 P3，且不阻塞主线。
- ❌ 不伪造客户 logo、下载量、性能数字等社会证明。
- ❌ 不引入前端框架（营销站手写 HTML 即可，与上游一致，便于回灌 PR）。
- ❌ 不改 server 镜像、不动数据卷、不给官网加登录门禁。

## 7. 视觉与技术选型

| 维度 | 决策 | 理由 |
|---|---|---|
| 技术栈 | **纯 HTML + CSS + 少量原生 JS**，Node 标准库白名单构建 | 沿用上游 `website/`（已被验证、可回灌 PR）；营销站不需要框架 |
| 样式来源 | 令牌与字体复用 `/opt/owndsh/docs-assets`（`theme.css` 已是令牌真源 + Inter/JetBrains 自托管） | 与控制台/帮助中心/API 参考同一视觉家族，避免第四套配色 |
| 营销化增强 | 更大的字号阶梯（hero 44–56px）、更宽留白、分区背景、克制的入场动效（遵守 `prefers-reduced-motion`） | 参考站都是"克制但精致"，不做花哨动效 |
| 双语排版 | 中文主标题 + 英文小标（`IDENTITY` / `GOVERN` / `SCALE`），与参考站一致 | 提升专业感，且为 P3 英文站铺路 |
| 截图 | 只用真实界面截图；没准备好的位置**留占位说明而不是插画** | 参考站全部使用真实截图；本部署有真实控制台可截 |
| 图片 | 现代格式 + 显式 `width/height`（防 CLS）+ 体积预算（首屏 ≤ 400 KB） | 上游官网整站 1.1 MB，多页后需要预算约束 |
| 第三方 | **零外部请求**（无 CDN、无分析、无 Google Fonts），`_headers`/CSP 同上游 `website/_headers` | 离线可用 + 合规 + 与文档站策略一致 |
| 构建 | `node build.mjs` 白名单发布 + **新增门禁**：链接/资源完整性、SEO 元数据必填、外部请求白名单、图片体积预算 | 复用本次会话已验证的三道防线思路 |

## 8. SEO 与可发现性（与文档站相反的立场）

| 项 | 官网（公开） | `/help/`、`/api-docs/`（内部） |
|---|---|---|
| robots | `index,follow` + 自有 `robots.txt` | `noindex, nofollow`（响应头） |
| sitemap | **`/sitemap.xml`（当前线上 404，必须补）** | 不提供 |
| 结构化数据 | `SoftwareApplication` JSON-LD（name/description/license/offers=免费/`sameAs` GitHub） | 不提供 |
| 每页元数据 | 独立 `title`/`description`/`canonical`/`og:*`/`twitter:card` | 单一标题即可 |
| 分享卡片 | 每页一张；**当前复用真实截图**（`assets/shots/*.jpg`），专用 1200×630 卡片列入 P3（门禁要求分享图必须真实存在） | 不需要 |
| 多语言 | `hreflang`（zh-CN / en），P3 落地 | 不需要 |
| 登录墙 | **不能有**（否则 SEO 与转化双输） | 必须有 |

## 9. 转化路径与"登录墙"处置（本项目特有的矛盾）

官网公开，但 **`/help/` 与 `/api-docs/` 目前都需要登录**。官网的"看文档"CTA 会撞到登录页，这会同时伤害转化与 SEO（爬虫只能看到 302）。

三种处置，推荐第 2 种：

| 方案 | 做法 | 代价 |
|---|---|---|
| 1. 保持现状 | 官网"文档"CTA 指向登录页 | 转化流失；爬虫看不到文档内容 |

### 上线后修复：HTML 注释嵌套导致头部注释泄漏（2026-09-16）

**症状**：官网每个页面底部多出一行裸文本：`。 [PROTOCOL]: 变更时更新此头部，然后检查 设计方案.md §4 -->`。
**根因**：`partials/nav.html` 与 `partials/footer.html` 的**文件头部注释内部**写了 `<!-- inject:nav -->` / `<!-- inject:footer -->`。
按 HTML 规则，注释体内出现 `-->` 会**立刻结束该注释**，该行之后的内容（`。`、`[PROTOCOL]` 行与结尾 `-->`）随即变成可见正文——
7 个页面各泄漏 2 处（导航片段与页脚片段各一）。
**修复**：片段头注释不再书写完整注释标记；`build.mjs` 新增**注释完整性门禁**：
① 注释体内不得含 `--`；② 不得嵌套注释；③ 剥离注释后不得残留 `[INPUT]/[OUTPUT]/[POS]/[PROTOCOL]` 标记。
已用修复前的产物反向验证：门禁检测逻辑能稳定报出泄漏。
**复核**：宿主侧脚本 `tools/check-html-comments.py` 对**三站共 11 个页面**逐一抓取检查，泄漏与嵌套注释均为 0。

> 教训：这不是"样式没生效"，而是**内容跑到了页面上**——只看截图或样式永远发现不了，
> 必须断言"可见文本里不该出现的东西没有出现"。同一思路已用于本项目的链接完整性、挂载可见性与 CSS 令牌三类门禁。
