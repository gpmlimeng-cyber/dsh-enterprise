# 连接器目标条文：万能连接（万物互联）

> 用户原话：「我的连接器目标是能作为 Agent **连接外部万物互联**，**万能连接**，
> 一切只要网络连通就能连接，**网络包括互联网、wifi、蓝牙等广义网络**」。

## 一、正确实现 = 三件套（不是"一个协议写一套"）

### ① 协议适配器框架
每个协议是一个**可插拔适配器**，对外只暴露**一套统一能力面**。目标覆盖（按优先级）：
```text
互联网:HTTPS · WebSocket · SSE · gRPC · MQTT · Webhook
局域网:HTTP(局域网设备)· mDNS/DNS-SD · SSDP/UPnP · DLNA · RTSP/ONVIF · SMB/NFS/FTP · IPP · SSH
近场:蓝牙经典 · BLE(GATT)· NFC · USB/串口 · 红外
工业/楼宇:Modbus · OPC-UA · KNX（经网关）
消息与身份:IM · 邮件 · 短信 · 电话
宿主自身(Android):摄像头 · 麦克风 · 传感器 · GPS · 通知（强权限门禁）
```
**加一个协议 = 写一个适配器**，上层（能力面、权限、审计、UI）不变。

### ② 发现层
"开箱即用"的来源是**自动发现**，不是让人填地址：
```text
局域网:mDNS/DNS-SD · SSDP/UPnP 广播 · 网段探测
近场:BLE 扫描 · NFC 碰一碰
云端:服务商注册表/目录（内置清单把认证与端点包好）
```
UI 上必须在"附近设备/可连接系统"里**看得见**，再决定连不连。

### ③ 统一能力面 + 三层权限
每个能力都要声明：读什么 · 写什么 · **会不会动物理世界**。
```text
L1 只读（查天气/读传感器/读文件）              → 可默认放行
L2 可逆写（发消息给自己/改开关/写文件）          → 授权即可
L3 不可逆物理动作（开门/断电/给客户发短信/下单/支付）→ 【每次显式确认，或由管理员策略锁死】
```
**这是"万能连接"与"出事故"的唯一分界线**：不可逆动作绝不允许"装一次就永久放行"。

## 二、与官方的关系（守宪法）

- 出站能力**优先生成官方 MCP/工具配置**，不另造运行时（避免"官方 UI 零分叉"被自己破）。
- 入站事件（IM/邮件/短信/设备事件）必须与服务端桥接配合（公网出口在服务端）→ 再推送到设备会话。
- 员工侧**不出现** MCP / BLE / GATT / Modbus / ONVIF / OAuth / webhook 等词 →
  统一表述为「连接」「已接好的系统」「附近设备」。

## 三、硬约束

1. **凭据引用化**：员工侧永远拿不到密钥；值只存服务端。
2. **出站 allowlist**：适配器能访问的域名/网段必须显式声明并被策略约束（防 SSRF 与横向移动）。
3. **入站验签 + 去重 + 幂等**：任何公网入口都按此三件套实现，并有审计。
4. **装前可见**：连接器在安装/启用前必须逐项列出"它能读/写/发什么"，含物理世界影响；
   附免责说明；装后可停用/卸载。
5. **诚实面对缺口**：我们**不做内容安全扫描**（社区事实标准同样如此）；
   信任只能靠"看得见的清单 + 装前告知 + 装后可撤回 + 三层权限"。
6. **不可逆动作默认最保守**：没有管理员策略或每次确认，L3 能力一律不可用。

## 五、必须满足 DSH 插件规范（用户追加的硬约束）

用户原话：「同时满足 **dsh 插件规范**」。即：**连接器内核与每个适配器都必须按官方插件规范交付，
不许另造一套平行运行时**。逐条合规清单：

1. **交付形态**：一律是官方 bundle/plugin（`package.json` 带 `dsh.bundle.patch` + `cordis.patch.yml`）；
   安装/升级/卸载走官方 `plugin_manager` 与 profile patch，不引入第二种安装器。
2. **能力注册**：使用官方 Cordis 插件生命周期与 `ctx.*` 服务；不私改官方包、不 fork、不做"影子注册"。
3. **UI**：只用官方 slots 与 primitives（`--dsw-*` token）；连接器页面进入官方既有的面板/槽位体系。
4. **MCP**：出站能力**生成官方的 MCP 连接配置**，不在我们这边另写一个 MCP 客户端运行时。
5. **preset/composition**：连接器的挂载遵从官方 preset 语义（一份 preset = 一份 Cordis entry list；
   模型/沙箱/工作区仍归 Host 组合，连接器不许越权拥有）。
6. **依赖规则**：对 `@deepseek-ai/*` 一律 peer 依赖，不打包官方运行时；版本区间显式声明。
7. **可插拔边界**：我们自己的"适配器框架"是**插件内部**的实现细节；对外仍表现为
   "一个官方插件 + 它声明的能力"，不让用户看到第二套概念。

**权威来源**：本会话技能目录里的官方技能 `cordis-plugin-development`
（描述覆盖"插件、bundle、功能、页面、面板、工具、**MCP 连接**"的设计/安装/配置）。
两路连接器规划都必须先通读它，把上表逐条对照官方规范落实，**不得以口述代替规范**。

## 六、跨平台要求（用户追加的硬约束）

用户原话：「**不要局限本机环境，我们未来的环境也是适配几大操作系统的**」。

### 6.1 架构必须分两层

**第一层 · 跨平台核心（必须 100% 平台无关，禁止 import 任何平台专有模块）**
- 能力模型（状态寻址 + 效果声明 + 可逆性 + 影响半径）
- 网络类适配器：MCP · HTTP/OpenAPI · A2A · ACP · IM/webhook · 邮件 · MQTT 等（本就只靠网络，天然全平台）
- 网络发现：mDNS · SSDP · 网段探测
- 策略与同意 · 审计与观测 · 目录与市场条目
→ 同一份代码跑在 Windows / macOS / Linux / Android。

**第二层 · 主机能力面（放在统一抽象如 `HostCapability` 后面，按平台实现）**
- 蓝牙/BLE · NFC · USB/串口 · 通知 · 传感器 · 摄像头 · 麦克风 · 定位 · 剪贴板 · 短信/电话
- Android：宿主 Android API / Shizuku / 无障碍（本会话已有先例）
  Windows：WinRT / WinUSB / Bluetooth API · macOS：CoreBluetooth / IOKit · Linux：BlueZ / udev
- 每个能力必须能回答【三态】：**可用 / 需用户手动确认 / 本平台不支持**；
  "不支持"必须显式呈现，**不允许静默失败**。

### 6.2 三条硬性纪律

1. **核心层必须在没有平台垫片的情况下也能编译与运行**（平台模块条件加载，不静态 import）。
2. **市场条目必须声明平台要求** —— 只支持 Windows 的连接器不该出现在 Android 的列表里；
   这给"可见性"增加了一个新维度：除组织/角色外，还要按**平台与宿主能力**过滤。
3. **企业服务端保持操作系统无关**（容器化交付）。

### 6.3 对既有表述的修正

前文若有"手机/设备"中心的表述，一律按本节修正为"宿主"：
宿主可能是手机、桌面机、也可能是无界面的服务器进程；能力面按宿主实际提供的为准。

## 四、验收

- 北极星不变：**新员工 ≤3 分钟做出第一件有价值的事、无需培训**；
  连接器侧对应的是"连上一个系统/设备"不超过三步，且默认就有可用的内置连接。
- 每个协议适配器上线时，必须同时交付：发现方式 · 能力清单 · 权限层级 · 试连（人话失败）· 审计事件。
