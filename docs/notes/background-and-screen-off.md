# 待办：息屏后实例是否继续运行（用户要求「以后再说」）

> 状态：**已记录，暂不投入**。探针仍在跑，数据白捡；等以后再研判。

## 要回答的问题

手机**息屏**之后，DSH 实例（以及它内部正在跑的代理/长任务）会不会被系统冻结或杀掉。

## 已确认的机制（本机实据）

```text
壳进程 com.deepcode.shell                     ← App 主进程
  └─ 引擎 node …/dsh/lib/bin.js web --port 3081  ← 引擎是【壳的子进程】，不是独立进程
       └─ 各代理/后台作业都在【引擎进程内】
实测：壳曾连续存活 81 分钟；引擎因我主动重启而只活 26 分钟（两者寿命不同源）
```

推论：**引擎的存活性 = App 进程的存活性**。息屏后是否继续跑，取决于：
Doze / App Standby（灭屏静置数十分钟起）、厂商省电策略（部分 ROM 几分钟就冻结）、
内存压力回收 cached 进程。

## 可调的杠杆（都在系统/App 设置里，插件侧无法替代）

1. 设置 → 应用 → DeepSeek Harness → 电池 → **无限制 / 不受限制**（不要"智能省电/自动管理"）
2. **App 自身设置里找「保持唤醒 / wakelock / 后台保持」** —— 该 App 是 Termux 系环境，
   Termux 有 “Acquire wakelock” 同类开关；若有，这是**最直接的杠杆**
3. 多任务界面把 App **加锁**（部分 ROM 有"锁定"按钮，防一键清理）
4. 跑长任务时**别从多任务里划掉**（划掉必断）
5. 开发者选项 →「充电时不锁定屏幕」（仅充电时有效，但很稳）

## 已布置的探针

```text
文件：~/.sshwork/screenoff-probe.log（约每 30 秒一行，共 2 小时）
读法：相邻两行间隔 ≈30 秒 = 正常；出现 >> 30 秒的间隔 = 那段时间被冻结/杀掉
注意：探针本身也活在引擎进程里 —— 若 App 被杀，探针会一起停（这本身就是判据）；
      而 App 重启后探针不会自动续（需重新布置）
```

## 长任务的稳妥做法（不依赖手机是否息屏）

```text
把耗时工作放到【远端服务器】用 nohup 挂住（7×24，与手机息屏无关），
本机只负责派发与收结果；本机中途断了也不影响远端执行。
```
