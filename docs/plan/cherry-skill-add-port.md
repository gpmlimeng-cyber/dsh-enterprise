# Cherry Studio「添加技能」移植：决策与排期

- **日期**：2026-10-05
- **上游**：Cherry Studio **2.1.4**（完整源码，本机 `/tmp/cherry/cherry-studio-main`，非打包产物）
- **事实真源**：[cherry-skill-add-2026-10-05.md](../research/cherry-skill-add-2026-10-05.md)（已入库 `18c9bc1`）
- **一句话**：Cherry 的「添加技能」是一个**下拉菜单**，四项分别是「通过 Agent 创建 / 在线搜索 / 系统搜索 / 本地导入」；
  本轮决定**四路全要**，但按依赖分五刀落地，且**三方来源复用我们已有的加固落盘路径**。

## 2. 设计地基：闸门在落盘处，不在来源处

**这是本刀最重要的一条，也是"灵活"与"安全"不打架的唯一解。**

用户的「企业有市场 ≠ 用户不能装三方」在技术上更精确的说法是：**我们与 Cherry 的差别不在"能不能装三方"，而在"装的东西走哪条路"**。

- Cherry 装三方 = `fetch` + 解包 + 拷进目录
- 我们装企业包 = 下载 + size/SHA-256 校验 + 解压前路径逃逸/符号链接门禁 + 原子改名 + 归属记录（`skill-install.ts`）

⇒ **三方安装复用同一条加固落盘路径，只换"来源"。** 否则每个来源一套闸门，就是三条来源三套漏洞。

### 三条**后移**（用户已拍板）

1. 装前三方来源的**风险提示弹窗**
2. **后台可见性 / 来源标记**
3. **审计**

### 三条**绝不移**（Lead 划的线，性质是"功能能不能正确工作"，不是"安全洁癖"）

1. **落盘仍走 `skill-install.ts`**（SHA-256 + 路径逃逸 + 符号链接 + 原子改名 + 归属记录）
   —— 它是安装功能能正确工作的前提。**不许为"快"新写一条更简单的落盘路径**，那会变成第二个实现（本项目已在"第二个实现"上栽过：官方弹层复刻那次）。
2. **ZIP 大小写/Unicode 折叠碰撞 + 路径逃逸**（`assertNoFoldedPathCollisions` 那一类）
   —— 这两条不是审计，是"装出来的东西是不是你以为的那个东西"。
3. **同名冲突预检**（沿用 `skill-install.ts:364` 既有那条，不新增规则）

> **判据一句话**：落盘正确性、路径不逃逸、冲突预检 = **功能**；风险提示、审计、可见性 = **可以后补**。

## 3. 五刀排期与依赖

```
刀 0（前置，阻塞中）  查明服务端验包收不收 skills/<name>/{references,scripts}/
   ├─→ 刀 2  纳入 skill-creator 成内置包（builtin=true 预装）
   └─→ 刀 3  三方来源（①在线搜索 ②系统搜索 ③本地导入）—— 取证已完成，可派
            └─→ 刀 4  成品回流（Agent 产出 → 企业后台）

刀 1（已落地）        「添加」下拉菜单 UI（执行不接）
```

| 刀 | 内容 | 依赖 | 状态 |
|---|---|---|---|
| **0** | 查明服务端 `SkillArtifactInspector` 收不收 `skills/<name>/` 下的资源文件 | — | ⛔ **未做**（要动 `server/**/src/main/**`，被"同包不并行"阻塞） |
| **1** | 「添加」下拉菜单 UI（四项，执行不接，全「开发中」） | — | ✅ **已落地**（`417a904`） |
| **2** | 纳入 `skill-creator` 成内置包，`builtin=true` 对全员预装 | 0 | ⬜ 未派 |
| **3** | 三方来源：在线搜索 / 系统搜索 / 本地导入 ZIP | 0 | ⬜ 未派（取证已回） |
| **4** | 成品回流：Agent 产出的技能目录 → 打包 `.dshskill` → 企业后台上传 | 2、3 | ⬜ **本轮不做**（见 §6） |

### 刀 0 为什么是硬前置

`skill-creator` 与三方来源下来的技能**都带资源文件**（`references/` / `scripts/` / `assets/`）。
我们 `.dshskill` 的服务端验包只接受**根 `manifest.json` 与 `skills/` 子树**（`SkillArtifactInspector.java:133-135`），
`skills/<name>/references/` **命中前缀、理应合法** —— 但**这是读代码推出的，不是实测**，必须实跑一次验包才能定打包形态。

> 本轮 GEB 教训：本项目已因"照想象写上游不存在的东西"栽过三次。刀 0 就是不再栽第四次。

## 5. 刀 1 的实现要点（已落地，留档供后续刀参照）

### 5.1 「添加」下拉

- **按页签取清单**的纯投影 `enterpriseAddMenuEntries(tab)`：本轮**只有 `skills` 有清单**，其余页签返回 `[]` ⇒ 渲染层 `return null`（**整段不渲染**，不画一枚点开是空的触发钮 —— 这是"预留"的正确表达）。
  将来填插件页签只是往投影里加一档，**组件不改**。
- 四项逐字照 Cherry `ResourceGrid.tsx:162-210`：`通过 Agent 创建` / `在线搜索` / `系统搜索` / `本地导入`（前两项在后两项之前，两个条件项在 Cherry 里是可缺席的）。
- 走**官方 `Menu` / `MenuItemButton` 原语**（`Menu` 的 `anchor` prop 允许调用方自带触发钮 ⇒ **零新增下拉语义**）。
- **四项全 `disabled`**，原因写在**可见标签**里（「…（开发中）」）。
  ★ **官方 `MenuItemButton` 不透传 `title`**（asar 逐字核过：只接 `{children, shortcut, icon, disabled, danger, separatorBefore, onSelect}`）⇒ 挂 `title` 会被静默丢弃，**那才是真的死控件**。产品宪法要的是"禁用即须有**可见**说明"，这条正好落在它上面。
- 触发钮 `aria-expanded`、**零 `aria-haspopup`**（本页有源码级反锁，禁 dialog 语义）。

### 5.2 版式

| 位置 | 取值 | 依据 |
|---|---|---|
| 工具行左端 | 四枚页签（灰底药丸轨道 + 选中项白胶囊） | 用户口径；药丸几何照参考图 |
| 工具行右端 | 搜索框**定宽 320px** + 漏斗筛选钮 | 用户口径「不撑满」；漏斗无外框照官方 `_iconButton`（`border:0;background:0 0`） |
| 中间 | `.own-market-rowBarSpacer`（`flex:1 1 auto`）吃空白 | 让右组整组贴右 |
| 标题行 | 刷新 + 「添加」两枚，右对齐 | 见下 |

**★ 标题行那两枚为什么改挂 `plugins.detail.badge` 槽**（用户口径：「刷新和添加应该和标题平行在一条线上……现在是在上方」）：

官方 `DetailTop`（`client.js:2193-2210`）的 DOM 是
`[data-plugin-item-detail] > _detailTop[_crumb, _detailHead[_cardIcon, actions槽]]`，
而标题在**另一棵子树** `_detailMain > _titleRow`（`client.js:2313-2321`）。

⇒ `plugins.detail.actions` 槽天生落在 `_detailHead`，它在 `_titleRow` **上方**（`margin:32px 0 0`），**怎么调 CSS 都只是把那一行挪位置，不会与标题同排**。
而 `plugins.detail.badge` 槽**就渲染在 `_titleRow` 里面**，且 `_titleRow` 是 `align-items:center` 的 flex
⇒ **走这个槽，与标题的垂直对齐由官方免费给到**，我们自己一个像素都不用算。

**连带效果**：撤掉 `plugins.detail.actions` 那处注册后，客户端注册面回到**四处**，`bundle.spec.ts` 里那条"期望 4 次、实际 5 次"的断言**自己转绿** —— 反证四处才是原本的形状。

### 5.3 两条"测试替实现打了工"的实证（下一刀必须引以为戒）

1. **`addMenuOpen` / `onToggleAddMenu` 没有任何供给点**（`client.tsx` 与控制器都不传）⇒ 真机上 `open` 恒 `undefined`、点击恒 no-op，**按钮点不开**；而单测直调时自己传了这两个 prop ⇒ **89 条测试全绿**。
   **修法**：状态由控制器 `useState` 持有（与 `filterOpen` 同一范式）并随**座位源**过树；`addMenuOpen` **必须进 `publish` 的签名**，否则点开不通知订阅者、菜单永远画不出来。
2. **在纯函数组件里放 `useState`** ⇒ `Cannot read properties of null (reading 'useState')`（测试直调时 dispatcher 为 null，本文件明令禁止）。

> **一般化的教训**：这类"props 可缺席 + 缺席静默 no-op"的契约，**任何单测都发现不了"真运行时没人传"**。
> 已建议加一条源码级反锁：`EnterpriseMarketShellProps` 上每个 `xxxOpen` / `onToggleXxx` 形状的可选 props，都必须能在 `client.tsx` 找到真实供给点，找不到就红。**（该反锁尚未落地，列为待办。）**

## 6. 刀 4（成品回流）本轮不做，及理由

Cherry **直写本机受管目录**（`$CHERRY_STUDIO_SKILLS_DIR`），所以它没有"产出物怎么回企业"这个问题。
我们是**企业管包**（后台上传 → 验包 → 发布 → 可见范围 → 员工端一键装）⇒ **Agent 产出的技能必须有一条回流通路**。

三条路：

| 方案 | 内容 | 代价 |
|---|---|---|
| 甲 | Agent 产出目录 → 提示用户手动上传后台 | 最省，但**断链** |
| 乙 | Host 侧包成 `.dshskill` → 走一个本机临时上传端点 | **要新增服务端能力** |
| **丙（本轮选）** | 先只做「跳新会话」，产出物由用户自己处理 | 与现状一致，**不倒退** |

**选丙的理由**：回流涉及**企业制品入库路径，是安全边界**，不该和 UI 一起做。先把"跳过去能用"打通，回流单独一刀设计。

## 7. 已知缺口 / 未决项

### 已补

- **ZIP 路径折叠碰撞**：Cherry 有 `assertNoFoldedPathCollisions`（`NFC().toLowerCase()`），我们**零命中**（阳性对照已重做）。`A.md` 与 `a.md` 在 macOS/Windows 落到**同一文件**，装出来是哪一个取决于哪条后写 —— 属**功能正确性**。**已于 `402187c` 补上**（含三条阳性对照）。

### 待裁 / 待做

1. **服务端验包收不收资源文件**（刀 0）—— 决定 `.dshskill` 能否装带 `references/` 的技能
2. **资源文件无单文件上限**（`256 KiB` 那条当前只管 `SKILL.md`）—— **双方共有的缺口**，需产品裁决
3. **每条 SKILL.md 的 256 KiB 上限是否也适用 `references/`** —— 同上
4. **那条源码级反锁**（§5.3）尚未落地
5. **Cherry 的「系统搜索」15 个目录**：我们只有 DSH 一个根（`~/.dsh/skills`）。要不要开放其它 CLI 目录是产品决策，**规模与风险都远超一次 UI 移植**

### 明确不做（本轮）

- 不复刻官方安装弹层（`openInstall` 不可达；复刻＝造第二套安装流程）
- 不新写落盘路径
- 不把风险提示 / 审计 / 后台可见性塞进刀 1~3（用户已后移）

3. 把 §2 的"闸门在落盘处"写成那份文档的**总纲**；
4. 本文件在刀 3 完成后**只保留决策与排期**，事实与规格全部回归那两份真源，避免第三份文档继续长。
